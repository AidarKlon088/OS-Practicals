## Цель

Воспроизвести гонку данных, исправить её с помощью `threading.Lock`, оценить цену
блокировки, реализовать безопасные переводы между счетами и схему
«производитель–потребитель» на ограниченной очереди.

## Объяснение кода

### race_demo.py

Инкремент разбит на чтение, `time.sleep(0)` и запись. Пока поток стоит между
чтением и записью, остальные читают то же старое значение, и все записывают
`value + 1`. Обновления теряются.

### lock_demo.py

```python
with lock:               # захват; освобождение — при выходе из блока
    value = counter
    time.sleep(0)
    counter = value + 1
```

`with lock:` делает чтение, переключение и запись одной **критической секцией**:
пока один поток внутри, другие ждут на `lock.acquire()`. Переключения потоков
остаются, но в секцию никто не входит, поэтому гонки нет. Для вариантов с `Lock`
проверяется `assert counter == 400000`.

### bank_demo.py

* У каждого счёта своя блокировка `Account.lock`.
* `transfer_safe()` захватывает **обе** блокировки всегда в одном порядке (по номеру
  счёта: `sorted(..., key=number)`). Если бы поток 1 брал A→B, а поток 2 B→A, они
  могли бы навсегда ждать друг друга — взаимоблокировка (подробнее в PR8).
* Проверка `src.balance < amount` выполняется внутри секции. Поэтому баланс не
  уходит в минус.
* Поток-аудитор во время работы берёт обе блокировки и проверяет, что
  `A + B == 2000`.
* В конце `assert` проверяет сумму, неотрицательность балансов, отсутствие
  нарушений у аудитора и что все 40 000 операций учтены.

### producer_consumer.py

* `queue.Queue` уже потокобезопасна (внутри — `Lock` и условные переменные).
* `q.put()` блокирует производителя, если в очереди 3 элемента; `q.get()` блокирует
  потребителя, если очередь пуста.
* Окончание работы передаётся «ядовитой пилюлей» `None`.
* Проверяется: все элементы получены в исходном порядке, размер очереди не превышал
  `maxsize`, `put()` действительно блокировался.

## Фактические результаты

### Гонка (`results_race_demo.txt`)

```text
Без блокировки, ожидаемо 400000
Запуск 1: counter = 100009, потеряно 299991, время 10.742 с
Запуск 2: counter = 100002, потеряно 299998, время 8.181 с
Запуск 3: counter = 100001, потеряно 299999, время 8.352 с
```

Потеряно ~75 % обновлений: почти всегда 4 потока читают одно значение, и из
четырёх инкрементов «выживает» один.

### Lock (`results_lock_demo.txt`)

| Вариант | counter (3 запуска) | Среднее время |
|---|---|---|
| 1. `counter += 1`, без Lock | 400000 ×3 | 0.012 с |
| 2. `counter += 1`, with lock | 400000 ×3 | 0.033 с |
| 3. read/sleep(0)/write, без Lock | 100000, 100003, 100000 | 11.294 с |
| 4. read/sleep(0)/write, with lock | 400000 ×3 | 42.544 с |

Все `assert` для вариантов с `Lock` пройдены.

**Наблюдения:**

* Вариант 1 на Python 3.14 дал верный результат: интерпретатор редко переключает
  потоки посреди `counter += 1`. Это **не гарантия**: операция не атомарна, и на
  другой версии Python или без GIL (free-threaded сборка) значения теряются.
* Цена `Lock` на быстрой операции — замедление в **2.7 раза** (захват и
  освобождение на каждой итерации).
* Вариант 4 медленнее варианта 3 почти в 4 раза. Внутри секции `sleep(0)` отдаёт
  CPU, но другие потоки не могут войти и снова засыпают на блокировке. Работа
  фактически идёт последовательно, плюс переключения. Поэтому критическую секцию
  нужно делать как можно короче и не ждать внутри неё.

### Банк (`results_bank_demo.txt`, `results_bank_demo_unsafe.txt`)

| Режим | Выполнено / отклонено | Итог A, B | Сумма | Нарушений у аудитора | Время |
|---|---|---|---|---|---|
| с блокировками | 38047 / 1953 | 1219, 781 | **2000** | 0 из 1624 | 3.987 с |
| `--unsafe` | 39449 / 551 | 7769, 10523 | **18292** | 786 из 787 | 0.872 с |

Без блокировок денег стало на 16 292 больше. Поток читает старый баланс `src`,
другой поток в это время уменьшает его. Затем первый записывает
`старое − amount` и затирает чужое списание, а зачисление на `dst` остаётся.
Безопасный режим медленнее в ~4.6 раза, зато результат правильный.

## Выводы

* Операции «прочитать–изменить–записать» над общими данными не атомарны. Без
  синхронизации обновления теряются (race_demo: −75 %, банк: сумма 18292 вместо 2000).
* `Lock` гарантирует правильный результат, но стоит времени (2.7× на простом
  инкременте). Критическая секция должна быть короткой.
* Несколько блокировок нужно захватывать в едином порядке, иначе возможна
  взаимоблокировка.
* Для обмена данными между потоками удобнее готовые потокобезопасные структуры
  (`queue.Queue`): они сами блокируют и будят потоки.

## Ответы на контрольные вопросы

> Вопросы методички недоступны; ниже — ответы на типовые вопросы по теме.

1. **Что такое состояние гонки?** Результат зависит от порядка выполнения потоков
   при одновременном доступе к общим данным, когда хотя бы один из них пишет.
2. **Что такое критическая секция?** Участок кода с доступом к общему ресурсу,
   который одновременно может выполнять только один поток.
3. **Как работает `Lock`?** `acquire()` захватывает блокировку или ждёт её
   освобождения; `release()` освобождает. `with lock:` вызывает их автоматически,
   даже при исключении.
4. **Почему `counter += 1` не атомарен?** Это чтение, сложение и запись — между ними
   поток может быть вытеснен.
5. **Lock и семафор — в чём разница?** `Lock` пускает в секцию один поток; семафор
   со счётчиком N — до N потоков одновременно.
6. **Зачем ограничивать размер очереди?** Чтобы быстрый производитель не занял
   всю память. Заполненная очередь притормаживает его до скорости потребителя
   (backpressure).
7. **Как избежать взаимоблокировки при нескольких Lock?** Захватывать их всегда в
   одном глобальном порядке (как в `bank_demo.py`).
