# PR7 — Межпроцессное взаимодействие (вариант A)

> **Важно.** Методичка PR4–PR8 при выполнении не была доступна. Работа сделана по теме
> «Межпроцессное взаимодействие» и охватывает основные механизмы IPC в Linux: неименованный
> канал, именованный канал (FIFO), разделяемую память и сигналы. Перед сдачей сверьте
> задания и контрольные вопросы с методичкой.

## Цель

Научиться передавать данные между процессами с помощью каналов, FIFO и разделяемой
памяти, управлять процессами через сигналы и увидеть, что разделяемая память
между процессами так же требует синхронизации, как общая переменная между потоками (PR6).

| Файл | Назначение |

поэтому работают только в Linux.

## Объяснение кода

### pipe_demo.py — неименованный канал

* `os.pipe()` возвращает два дескриптора: `r` (чтение) и `w` (запись). После `fork()`
  они есть и у родителя, и у потомка.
* Канал однонаправленный, поэтому для запроса и ответа созданы **два** канала:
  родитель → потомок (текст) и потомок → родитель (`строки слова символы`).
* Каждый процесс **закрывает ненужные концы**. Это важно: `read()` вернёт EOF (0 байт)
  только когда закрыты *все* дескрипторы записи. Если потомок не закроет свою копию
  `to_child_w`, он будет вечно ждать данных от самого себя.
* Ёмкость: `fcntl(F_GETPIPE_SZ)` и запись в канал в режиме `O_NONBLOCK` до
  `BlockingIOError` — так видно, сколько данных ядро держит в буфере канала.
* Скорость: потомок пишет 64 МБ блоками по 64 КБ, родитель читает и считает байты.

### fifo_reader.py / fifo_writer.py — именованный канал

* `os.mkfifo()` создаёт специальный файл типа `p`. Данные через диск не идут —
  это тот же канал в ядре, но с **именем в файловой системе**. Поэтому его могут
  открыть процессы, которые не связаны родством (два терминала).
* `open()` на чтение **блокируется**, пока кто-то не откроет FIFO на запись (и наоборот).
* Писатель вызывает `flush()` после каждой строки, иначе данные остались бы в
  буфере Python. Закрытие FIFO писателем даёт читателю EOF, и цикл `for line in fifo`
  заканчивается.

### shm_demo.py — разделяемая память

* Шаг 0: процессы `multiprocessing.Process` увеличивают обычную глобальную
  переменную. У каждого процесса своя копия, родитель видит 0.
* `SharedMemory(create=True, size=8)` создаёт файл `/dev/shm/psm_…`. Каждый процесс
  подключается к нему по имени и отображает его в своё адресное пространство
  (`mmap`). Запись одного процесса сразу видна другим, без копирования через ядро.
* Счётчик хранится как 8-байтовое целое (`struct.pack_into("q", …)`): чтение и
  запись — два отдельных шага, как в PR6.
* `multiprocessing.Lock` — межпроцессная блокировка (POSIX-семафор), в отличие от
  `threading.Lock`, который работает только внутри одного процесса.
* `unlink()` удаляет сегмент. Без него файл остался бы в `/dev/shm` после выхода.

### signals_demo.py — сигналы

* `signal.signal(SIGUSR1, handler)` устанавливает обработчик, `os.kill(pid, sig)`
  посылает сигнал, `signal.pause()` ждёт сигнала.
* Чтобы родитель не послал сигнал раньше, чем потомок установит обработчики (тогда
  `SIGUSR1` убил бы потомка действием по умолчанию), потомок сообщает «готов» через канал.
* `SIGTERM` обрабатывается «корректно»: потомок завершается с кодом, равным числу
  полученных `SIGUSR1`, и родитель проверяет этот код через `waitpid()`.
* `pthread_sigmask(SIG_BLOCK)` откладывает доставку сигнала, `sigpending()` показывает
  ожидающие сигналы.

## Фактические результаты

### Неименованный канал (`results_pipe_demo.txt`)

```text
  родитель PID=478, потомок PID=479
  дескрипторы: to_child=(3, 4), to_parent=(5, 6)
  родитель отправил 302 байт и закрыл конец записи
  ответ потомка (строки слова символы): 4 24 165
  assert: ответ совпадает с подсчётом родителя (4 24 165) — OK

  F_GETPIPE_SZ = 65536 байт, PIPE_BUF (атомарная запись) = 4096 байт
  записано без чтения (O_NONBLOCK): 65536 байт, следующий write() -> BlockingIOError

  получено 67108864 байт за 0.068 с — 936 МБ/с
```

* Отправлено 302 **байта**, но 165 **символов**: русские буквы в UTF-8 занимают 2 байта.
* Буфер канала в Linux — 64 КБ. Когда он полон, `write()` блокируется (или получает
  `EAGAIN` в неблокирующем режиме). Писатель ждёт читателя, как в очереди
  `maxsize=3` в PR6.
* Запись не больше `PIPE_BUF` = 4096 байт атомарна: данные нескольких писателей не перемешиваются.

### FIFO (`results_fifo.txt`)

```text
[reader] PID=521 PPID=476, FIFO /tmp/pr07.fifo (prw-------)
[reader] open() на чтение — жду писателя...
$ ls -l /tmp/pr07.fifo
prw------- 1 user user 0 Oct 28 21:27 /tmp/pr07.fifo
[writer] PID=524 PPID=476, открываю /tmp/pr07.fifo на запись
[reader] писатель подключился, open() ждал 1.02 с
[reader] получено: сообщение 1 от PID 524 в 21:27:14
...
[reader] получено: сообщение 5 от PID 524 в 21:27:15
[writer] FIFO закрыт — читатель получит EOF
[reader] EOF, всего сообщений: 5
[reader] FIFO удалён: exists = False
```

* Тип файла `p` и размер **0**: данные в FIFO не хранятся на диске.
* Читатель ждал в `open()` 1.02 с — ровно столько, сколько скрипт выжидал перед
  запуском писателя.
* Процессы 521 и 524 не родитель и потомок друг для друга (оба — дети shell 476):
  их связывает только имя `/tmp/pr07.fifo`.

### Разделяемая память (`results_shm_demo.txt`)

```text
Метод запуска процессов: forkserver, ядер: 20
  [процесс 485] своя копия plain_counter = 1000
  [процесс 486] своя копия plain_counter = 1000
  в родителе plain_counter = 0 (изменения потомков не видны)
  создан сегмент psm_a511ec62: /dev/shm/psm_a511ec62 существует = True, размер = 8 байт
  после unlink(): существует = False
```

| Вариант (4 процесса × 50 000) | counter (3 запуска) | Среднее время |
|---|---|---|
| без Lock | 6789, 5823, 4573 (потеряно ~97 %) | 0.060 с |
| с `multiprocessing.Lock` | 200000 ×3 | 0.695 с |

* Без блокировки потеряно **97 %** обновлений, хотя здесь нет `sleep(0)`. В PR6 простой
  `counter += 1` в потоках не терял значения из-за GIL. Здесь у каждого процесса свой
  интерпретатор и свой GIL, и 4 процесса работают на разных ядрах **одновременно**.
  Процессы постоянно перезаписывают общую ячейку своими устаревшими значениями.
* С `Lock` результат точный, но в **11.5 раза** медленнее. Это больше, чем 2.7× в PR6:
  межпроцессный семафор при конкуренции требует системных вызовов (`futex`) и
  переключений между процессами.

### Сигналы (`results_signals_demo.txt`)

```text
1. Обработчики сигналов
  родитель 515 -> потомок 516: 5 x SIGUSR1 (пауза 0.05 с), SIGUSR2, SIGTERM
  [потомок 516] SIGUSR2: получено SIGUSR1 = 5
  [потомок] SIGTERM: корректное завершение, код 5
  родитель: код завершения потомка = 5

2. Заблокированные сигналы не накапливаются
  родитель: отправил 5 x SIGUSR1, пока они заблокированы у потомка
  [потомок] ожидающие (pending) сигналы: ['SIGUSR1']
  [потомок] после разблокировки обработчик вызван 1 раз

3. SIGKILL нельзя перехватить
  signal.signal(SIGKILL, ...) -> OSError: [Errno 22] Invalid argument
  потомок 518 игнорирует SIGTERM: через 0.2 с жив = True
  после SIGKILL: waitstatus_to_exitcode = -9 (SIGKILL)
```

* Ядро хранит для обычного сигнала только **флаг** «ожидает», а не счётчик. Пять
  заблокированных `SIGUSR1` превратились в один. Поэтому сигналы подходят для
  уведомлений («что-то произошло»), но не для передачи данных или точного подсчёта событий.
* `SIGTERM` можно перехватить или проигнорировать — это «вежливая» просьба завершиться.
  `SIGKILL` ядро выполняет само, и обработчик для него установить нельзя.

### Shell (`results_shell.txt`)

```text
$ ps -e | wc -l
32
$ ls -l /proc/self/fd | cat
l-wx------ 1 user user 64 Oct 28 21:27 1 -> pipe:[12599]
$ mkfifo /tmp/pr07_shell.fifo && ls -l /tmp/pr07_shell.fifo
prw-r--r-- 1 user user 0 Oct 28 21:27 /tmp/pr07_shell.fifo
$ echo 'привет через FIFO' > /tmp/pr07_shell.fifo &  cat /tmp/pr07_shell.fifo
привет через FIFO
```

Оператор `|` в shell — это тот же `pipe()`: стандартный вывод `ls` (дескриптор 1)
указывает на объект ядра `pipe:[12599]`.
(Дескриптор 0 тоже оказался каналом, потому что скрипт запускался не из
интерактивного терминала. В обычном терминале там будет `/dev/pts/N`.)

## Сравнение механизмов

| Механизм | Кто может общаться | Данные | Синхронизация | Результат здесь |
|---|---|---|---|---|
| pipe | родственные процессы (через `fork`) | поток байтов, одно направление | встроена: `read` ждёт данных, `write` ждёт места | 936 МБ/с |
| FIFO | любые процессы, знающие имя | поток байтов | встроена, `open()` ждёт второй стороны | 5 сообщений между независимыми процессами |
| разделяемая память | любые, знающие имя сегмента | общая область памяти, без копирования | **нет** — нужен `Lock`/семафор | без Lock −97 %, с Lock точно |
| сигналы | любые процессы (по PID, при наличии прав) | только номер сигнала | асинхронно, не накапливаются | 5 → 1 при блокировке |

## Выводы

* У каждого процесса своё адресное пространство, поэтому общаться процессы могут
  только через механизмы ядра.
* Каналы и FIFO сами синхронизируют писателя и читателя (блокировки на пустом и
  полном буфере). Их проще использовать правильно, но данные копируются через ядро.
* Разделяемая память — самый быстрый способ без копирования, но без явной
  синхронизации данные теряются ещё сильнее, чем у потоков, так как процессы
  выполняются по-настоящему параллельно.
* Сигналы — асинхронные уведомления. Они не несут данных и могут «склеиваться».
  `SIGKILL` и `SIGSTOP` перехватить нельзя.

## Ответы на контрольные вопросы

> Вопросы методички недоступны; ниже — ответы на типовые вопросы по теме.

1. **Что такое IPC и зачем оно нужно?** Механизмы обмена данными и синхронизации
   между процессами, у которых изолированная память: каналы, FIFO, разделяемая
   память, очереди сообщений, семафоры, сигналы, сокеты.
2. **Чем именованный канал отличается от неименованного?** Неименованный существует
   только как пара дескрипторов и передаётся потомкам через `fork()`. FIFO имеет имя в
   файловой системе (`mkfifo`), и его может открыть любой процесс с правами доступа.
3. **Когда `read()` из канала возвращает 0?** Когда буфер пуст и закрыты все
   дескрипторы записи (EOF). Если хотя бы один дескриптор записи открыт, `read()` ждёт.
4. **Что будет при записи в канал, который никто не читает?** Если закрыты все
   концы чтения — процесс получит `SIGPIPE` (или ошибку `EPIPE`). Если читатель есть,
   но не читает — `write()` заблокируется, когда буфер (64 КБ) заполнится.
5. **Почему разделяемая память быстрее каналов?** Данные не копируются в ядро и
   обратно: процессы обращаются к одним и тем же физическим страницам памяти.
   Цена — синхронизацию нужно делать самому.
6. **Какие сигналы нельзя перехватить?** `SIGKILL` (9) и `SIGSTOP` (19).
7. **Чем `SIGTERM` отличается от `SIGKILL`?** `SIGTERM` (15) — запрос на завершение:
   процесс может перехватить его, сохранить данные и выйти. `SIGKILL` завершает
   процесс немедленно, без участия процесса.
8. **Чем `multiprocessing.Lock` отличается от `threading.Lock`?** `threading.Lock`
   работает между потоками одного процесса. `multiprocessing.Lock` основан на
   семафоре ядра и синхронизирует разные процессы.
