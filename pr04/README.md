## Цель

Научиться создавать потоки в Python (`threading`), увидеть гонку данных при работе
с общей переменной, посмотреть потоки процесса через `/proc` и сравнить
последовательную и многопоточную загрузку файлов.

## Объяснение кода

### threads_demo.py

* Потоки создаются ровно так, как требует задание:
  `threading.Thread(target=worker, args=(i,))`, затем `start()` и `join()`.
* `worker_plain` — обычный `counter += 1`.
* `worker_race` — инкремент разбит на 3 шага:
  ```python
  value = counter      # чтение
  time.sleep(0)        # явно отдаём CPU другому потоку
  counter = value + 1  # запись устаревшего значения
  ```
  Пока поток «спит» между чтением и записью, другие потоки читают то же
  старое значение. Затем все они записывают `value + 1` — обновления теряются.
* `show_proc_threads()` запускает 4 ждущих потока и читает:
  * строку `Threads:` из `/proc/PID/status`;
  * список каталогов `/proc/PID/task` — по одному на каждый поток (TID).

### download_demo.py

* Создаёт 20 файлов по 256 КБ во временном каталоге (удаляется автоматически).
* Поднимает `ThreadingHTTPServer` на `127.0.0.1` со случайным свободным портом.
* Скачивает файлы через `urllib.request` последовательно и через
  `ThreadPoolExecutor(max_workers=4)`, каждую пару измерений повторяет 3 раза.
* Два сценария: без задержки и с задержкой сервера 0.1 с на запрос (имитация
  сетевой задержки, т. е. ожидания ввода-вывода).
* `assert` проверяет, что скачанные байты совпадают с исходными.

## Фактические результаты

Количество ядер: `nproc` → **20**. Python 3.14.4 (сборка с GIL:
`sys._is_gil_enabled()` → `True`).

### Пять запусков — режим гонки (`threads_demo.py`)

|---|---|---|---|
| 1 | 100 001 | 299 999 | 10.118 |
| 2 | 100 001 | 299 999 | 9.691 |
| 3 | 100 000 | 300 000 | 12.031 |
| 4 | 100 000 | 300 000 | 8.742 |
| 5 | 100 001 | 299 999 | 10.797 |

Ожидалось 400 000, получено ≈ 100 000 — потеряно около 75 % обновлений.

| 4 | 400 000 | 0 | 0.014 |

### Потоки в /proc

```text

```

Первый TID совпадает с PID — это главный поток.

| Сценарий | Последовательно (среднее) | 4 потока (среднее) | Ускорение |
|---|---|---|---|
| localhost без задержки | 0.038 с | 0.053 с | 0.71× (медленнее) |
| задержка 0.1 с на запрос | 2.072 с | 0.539 с | 3.84× |

Полный вывод — в `results_download.txt`.

## Анализ результатов

1. **Почему `counter += 1` дал 400 000.** В CPython с GIL поток выполняется, пока
   интерпретатор не решит переключиться (интервал `sys.getswitchinterval()` = 5 мс,
   проверка — только в определённых точках байткода). На Python 3.14 переключение
   внутри `counter += 1` на практике не произошло, поэтому потерь не было. Это
   **не** гарантия корректности: операция не атомарна, и на другой версии или сборке
   (например, free-threaded Python) потери возможны.
2. **Почему в режиме race теряется ~75 %.** `time.sleep(0)` гарантирует
   переключение между чтением и записью. Все 4 потока читают одно и то же значение
   и пишут одно и то же `value + 1`, поэтому из 4 инкрементов «выживает» примерно
   один. Это классическая гонка данных (*race condition*): неделимой должна быть
   вся последовательность «прочитать-изменить-записать».
3. **Загрузка файлов.** Многопоточность **не всегда быстрее**:
   * на localhost без задержки каждый запрос занимает ~2 мс, и накладные расходы
     на пул потоков и конкуренцию за GIL оказались больше выигрыша — 4 потока
     были медленнее (0.71×);
   * когда запрос ждёт ввода-вывода (задержка 0.1 с), поток во время ожидания
     освобождает GIL, и 4 загрузки идут одновременно: 20 × 0.1 с ≈ 2 с против
     5 «волн» × 0.1 с ≈ 0.5 с — ускорение ≈ 3.8×, близко к теоретическим 4×;
   * 20 ядер почти не влияют на результат: задача ограничена ожиданием, а не CPU,
     а для CPU-задач GIL не даёт потокам Python работать параллельно.

## Выводы

* Поток в Linux — это отдельная задача ядра со своим TID, видимая в `/proc/PID/task`;
  все потоки процесса разделяют одно адресное пространство (общий `counter`).
* Доступ к общей переменной без синхронизации приводит к гонке и потере данных.
  Исправление с `threading.Lock` — в PR6 (`pr06/lock_demo.py`, основан на этом коде).
* Потоки в Python эффективны для задач, ограниченных вводом-выводом, и
  бесполезны или вредны для очень коротких операций, где накладные расходы больше выигрыша.

## Ответы на контрольные вопросы

> Вопросы методички недоступны; ниже — ответы на типовые вопросы по теме.

1. **Чем поток отличается от процесса?** Процесс имеет собственное адресное
   пространство и ресурсы; потоки одного процесса разделяют память, файлы и
   дескрипторы, но имеют свой стек, регистры и TID. Создание потока дешевле.
2. **Как в Linux посмотреть потоки процесса?** `/proc/PID/status` (поле `Threads`),
   каталог `/proc/PID/task`, `ps -T -p PID`, `top -H -p PID`.
3. **Что такое гонка данных?** Ситуация, когда результат зависит от порядка
   выполнения потоков, которые обращаются к общим данным (хотя бы один пишет)
   без синхронизации.
4. **Почему `counter += 1` не атомарна?** Она состоит из чтения, сложения и записи;
   между этими шагами может произойти переключение потоков.
5. **Что такое GIL и как он влияет на потоки?** Глобальная блокировка интерпретатора
   CPython: в каждый момент байткод выполняет только один поток. Для CPU-задач
   потоки не ускоряют работу; при ожидании I/O GIL освобождается, и потоки дают выигрыш.
6. **Когда многопоточность ускоряет программу?** Когда потоки большую часть времени
   ждут (сеть, диск), как показал сценарий с задержкой 0.1 с.
