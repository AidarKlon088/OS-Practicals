## Цель

Воспроизвести взаимоблокировку потоков, обнаружить её по графу ожидания, применить
методы предотвращения и избежания взаимоблокировок и проверить алгоритм банкира.

## Условия Коффмана

Взаимоблокировка возможна, только если одновременно выполнены **все четыре** условия:

| Условие | В `deadlock_demo.py` | Как нарушается |
|---|---|---|
| Взаимное исключение | `Lock` может держать только один поток | (нельзя — блокировка для этого и нужна) |
| Удержание и ожидание | T1 держит A и ждёт B | официант / захват всех ресурсов сразу |
| Отсутствие вытеснения | `Lock` нельзя отобрать у владельца | таймаут с откатом: поток сам отдаёт A |
| Циклическое ожидание | T1 → B → T2 → A → T1 | **единый порядок захвата** |

## Объяснение кода

### deadlock_demo.py

* `TrackedLock` — обёртка над `threading.Lock`, которая запоминает владельца
  (`owner`) и какую блокировку ждёт каждый поток (`waiting`).
* `find_cycle()` строит **граф ожидания** (wait-for graph): ребро «поток → владелец
  блокировки, которую он ждёт». Цикл в этом графе — это взаимоблокировка.
* Чтобы взаимоблокировка возникала **всегда**, а не случайно, после захвата первой
  блокировки потоки встречаются на `threading.Barrier(2)`. К этому моменту каждый
  гарантированно держит свою первую блокировку.
* `thread_state()` читает `/proc/self/task/TID/stat` и `wchan`: видно, что
  заблокированные потоки спят в ядре, а не крутятся на CPU.
* Потоки создаются как `daemon=True`: заблокированные потоки нельзя «разбудить»,
  а daemon-потоки не мешают процессу завершиться.
* **ordered**: `sorted((first, second), key=name)` — оба потока берут сначала A, потом B.
* **timeout**: `second.acquire(timeout=0.01)`. При неудаче поток освобождает первую
  блокировку, ждёт случайное время (чтобы не повторять конфликт синхронно) и пробует снова.

### dining_philosophers.py

* 5 вилок — 5 `TrackedLock` (`F0…F4`), философ `Pi` берёт `Fi` и `F(i+1)`.
* **naive**: все берут левую вилку, затем правую. `Barrier(5)` после первой вилки
  гарантирует, что все держат по одной вилке, — образуется цикл из 5 философов.
* **ordered**: сначала вилка с меньшим номером. Для P0…P3 это левая вилка, а P4
  берёт сначала F0, потом F4. Цикл разорван.
* **waiter**: `Semaphore(4)` — к столу допускается не больше 4 философов, значит,
  на 5 вилок хотя бы один получит обе.
* Во время еды под отдельной блокировкой проверяется, что соседи не едят одновременно,
  и считается максимум одновременно едящих.

### bankers.py

* `Need = Max − Allocation`.
* `is_safe()` — алгоритм безопасности: ищет процесс с `Need ≤ Work`. Такой процесс
  может завершиться и вернуть ресурсы (`Work += Allocation`). Если так завершатся
  все — состояние безопасное. Просмотр идёт по кругу без возврата к P0 после каждого
  найденного процесса.
* `request_resources()` проверяет `Request ≤ Need`, затем `Request ≤ Available`, затем
  **пробно** выдаёт ресурсы и выполняет `is_safe()`. Если состояние небезопасное,
  запрос откладывается.
* `detect_deadlock()` — алгоритм обнаружения: вместо `Need` используется матрица
  текущих запросов `Request`. Процессы без ресурсов сразу считаются завершёнными.
  Оставшиеся незавершёнными — заблокированы.

## Ручной расчёт (алгоритм банкира)

Ресурсы A=10, B=5, C=7. `Available = (10,5,7) − Σ Allocation = (3,3,2)`.

| | Allocation | Max | Need |
|---|---|---|---|
| P0 | 0 1 0 | 7 5 3 | 7 4 3 |
| P1 | 2 0 0 | 3 2 2 | 1 2 2 |
| P2 | 3 0 2 | 9 0 2 | 6 0 0 |
| P3 | 2 1 1 | 2 2 2 | 0 1 1 |
| P4 | 0 0 2 | 4 3 3 | 4 3 1 |

Work = (3,3,2): P0 (7,4,3) — нет; **P1** (1,2,2) — да → (5,3,2); P2 (6,0,0) — нет;
**P3** (0,1,1) → (7,4,3); **P4** (4,3,1) → (7,4,5); второй круг: **P0** (7,4,3) → (7,5,5);
**P2** (6,0,0) → (10,5,7). Последовательность **<P1, P3, P4, P0, P2>** — безопасно.

* **P1 запрашивает (1,0,2)**: ≤ Need (1,2,2), ≤ Available (3,3,2). Пробно:
  Available = (2,3,0), Need P1 = (0,2,0). Последовательность снова <P1, P3, P4, P0, P2>
  (совпадает с учебником) → **выдать**.
* Затем **P4 (3,3,0)**: 3 > 2 по A → **ждать**.
* Затем **P0 (0,2,0)**: Available стал бы (2,1,0). Ни один `Need` не ≤ (2,1,0)
  (P1 нужен B=2, P3 нужен C=1) → **небезопасно, отказ** (как в учебнике).

Обнаружение (A=7, B=2, C=6, Available = 0): P0 (Request 0) → Work (0,1,0); P2 → (3,1,3);
P3 → (5,2,4); P4 → (5,2,6); P1 → (7,2,6). Блокировки нет. Если P2 запросит ещё 1 C,
после P0 Work = (0,1,0) и ни один запрос не выполним → **P1, P2, P3, P4 заблокированы**.

Программа дала ровно эти значения. `test_bankers.py`: **18 проверок, все пройдены**.

## Фактические результаты

### Взаимоблокировка двух потоков (`results_deadlock_demo.txt`)

```text
1. Взаимоблокировка: T1 берёт A -> B, T2 берёт B -> A
  T1: захватил A, хочу B
  T2: захватил B, хочу A
  через 2 с: T1 жив = True, T2 жив = True
  T1 (TID 541): состояние S, wchan = futex_do_wait
  T2 (TID 542): состояние S, wchan = futex_do_wait
  граф ожидания: T2 --ждёт A--> T1 --ждёт B--> T2
```

* Оба потока в состоянии **S** (sleeping), `wchan = futex_do_wait`: они спят в ядре на
  futex и CPU не тратят. Снаружи процесс выглядит «просто зависшим». Найти причину
  помогает только граф ожидания.
* Цикл `T2 → A → T1 → B → T2` — классическое циклическое ожидание.

| Режим | Результат | Время | Откатов |
|---|---|---|---|
| единый порядок A→B | 20 000 из 20 000 | 0.030 с | — |
| таймаут + откат | 20 000 из 20 000 | 0.045 с | T1 = 0, T2 = 2 |

Таймаут медленнее: при конфликте поток ждёт 0.01 с, откатывается и спит. Откаты
произошли только на первой, специально спровоцированной итерации. Дальше потоки
редко сталкиваются, потому что держат блокировки очень недолго.

### Обедающие философы (`results_dining_philosophers.txt`)

```text
Стратегия naive: левая, затем правая вилка (наивно)
  через 2 с: живых потоков 5 из 5, съедено обедов 0
  вилки заняты: F0=P0, F1=P1, F2=P2, F3=P3, F4=P4
  граф ожидания: P4 --ждёт F0--> P0 --ждёт F1--> P1 --ждёт F2--> P2 --ждёт F3--> P3 --ждёт F4--> P4
```

| Стратегия | Обедов | Время | Ожидание вилок P0…P4, с | Макс. едят сразу |
|---|---|---|---|---|
| naive | 0 (взаимоблокировка) | — | — | — |
| ordered | 100 × 5 | 0.379 с | 0.168 / 0.130 / 0.118 / 0.111 / 0.175 | 2 |
| waiter | 100 × 5 | 0.610 с | 0.391 / 0.399 / 0.397 / 0.399 / 0.401 | 2 |

* В обоих рабочих вариантах соседи **ни разу** не ели одновременно, и больше 2 философов
  (= 5 // 2) за раз не ели.
* **ordered** быстрее, но несимметричен: P0 и P4 ждут дольше остальных, так как оба
  начинают с одной и той же вилки F0 и конкурируют за неё.
* **waiter** медленнее (лишний семафор, и за столом не больше 4), зато ожидание
  распределено равномерно.

### Алгоритм банкира (`results_bankers.txt`)

```text
  безопасно: True, последовательность <P1, P3, P4, P0, P2>
2. Запрос P1 (1, 0, 2)
  выдано: True
3. Новые запросы в этом состоянии
  P4 (3, 3, 0): отказ: ресурсов недостаточно — процесс ждёт
  P0 (0, 2, 0): отказ: состояние стало бы небезопасным — запрос отложен
  P2 (1, 0, 0): выдано, последовательность <P1, P3, P4, P2, P0>
  P3 (0, 1, 1): отказ: ресурсов недостаточно — процесс ждёт
4. Обнаружение взаимоблокировки (A=7, B=2, C=6)
  заблокированы: нет, порядок завершения <P0, P2, P3, P4, P1>
5. P2 запрашивает ещё 1 экземпляр C: Request[P2] = (0, 0, 1)
  заблокированы: <P1, P2, P3, P4>, могут завершиться: <P0>
```

Запрос P0 (0,2,0) **меньше** доступных ресурсов, но всё равно отклонён. Банкир
отказывает не из-за нехватки ресурсов сейчас, а потому что после выдачи может
наступить взаимоблокировка. Небезопасное состояние — ещё не взаимоблокировка, но
система её уже не может гарантированно избежать.

## Выводы

* Взаимоблокировка возникает при одновременном выполнении четырёх условий Коффмана.
  Нарушить достаточно одно.
* Самый практичный способ — **единый порядок захвата ресурсов**: он прост, без накладных
  расходов и сразу исправил оба примера (два потока, философы).
* Таймауты с откатом спасают, когда порядок задать нельзя, но добавляют задержки и
  риск livelock (поэтому пауза случайная).
* Алгоритм банкира гарантирует отсутствие взаимоблокировок, но требует заранее знать
  максимальные потребности (`Max`) и проверяет состояние при каждом запросе. Поэтому
  в ОС общего назначения он почти не используется.
* Взаимоблокированные потоки не потребляют CPU (состояние `S`). Обнаружить их можно
  только по графу ожидания или алгоритму обнаружения.

## Ответы на контрольные вопросы

> Вопросы методички недоступны; ниже — ответы на типовые вопросы по теме.

1. **Что такое взаимоблокировка?** Ситуация, когда группа процессов (потоков) ждёт
   ресурсы, которые удерживают другие процессы этой же группы, и никто не может продолжить.
2. **Назовите условия Коффмана.** Взаимное исключение, удержание и ожидание,
   отсутствие вытеснения, циклическое ожидание.
3. **Какие есть подходы к взаимоблокировкам?** Предотвращение (нарушить одно из
   условий), избежание (алгоритм банкира), обнаружение и восстановление (граф ожидания,
   завершение или откат процессов), игнорирование («алгоритм страуса» — так поступают
   большинство ОС).
4. **Чем безопасное состояние отличается от небезопасного?** В безопасном существует
   последовательность, в которой все процессы могут завершиться. Небезопасное — не
   обязательно взаимоблокировка, но её уже нельзя гарантированно избежать.
5. **Что такое граф распределения ресурсов / граф ожидания?** Ориентированный граф
   «процесс → ресурс → процесс-владелец». При единственном экземпляре каждого ресурса
   цикл в нём означает взаимоблокировку.
6. **Чем livelock отличается от deadlock?** При livelock процессы активны и постоянно
   меняют состояние (например, одновременно откатываются и повторяют), но работа не
   продвигается. При deadlock они спят.
7. **Как решить задачу об обедающих философах?** Упорядочить вилки (брать сначала с
   меньшим номером), ограничить число философов за столом (официант / семафор N−1),
   брать обе вилки атомарно или использовать асимметрию (чётные берут левую, нечётные — правую).
